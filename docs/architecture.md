# Архитектура и границы

## Цель

Упростить сборку одной конфигурации кампании и безопасно менять привязки офферов, сохраняя возможность увидеть незавершённые операции и восстановить удалённую привязку

## Структура

```text
app/
  config.py       настройки и валидация .env
  main.py         FastAPI, маршруты, схемы ответов, авторизация, ошибки, probes
  keitaro.py      единственная граница внешних HTTP-запросов
  services.py     создание, операции/шаги, редактор и публикация
  domain.py       расчёт долей, канонизация снимков
  schemas.py      DTO и валидация входа/выхода
  models.py       модели SQLAlchemy
  db.py           engine и session factory
  locks.py        межпроцессная блокировка через БД
migrations/       Alembic
frontend/src/     React, TypeScript, API-клиент, стили, тесты
tests/            unit и интеграционные тесты
tools/            явный локальный симулятор и инструмент live smoke
```

Без микросервисов, очередей и общей распределённой транзакции; каждый сервис получает клиент и session factory через конструктор

## Хранение

`operations`: UUID, уникальный ключ идемпотентности, тип, хеш и нормализованный запрос, статус, внешние ID, результат, безопасная ошибка и время

`operation_steps`: FK операции, уникальная пара operation/name, число попыток, статус, снимки до/после и ошибка

`editor_streams`: внешний ID потока, ID кампании, последний снимок Keitaro, baseline, draft, archive, версия, dirty, незавершённая публикация и время синхронизации

Состав локальных привязок хранится JSON-массивами как единый агрегат потока, чтобы атомарно менять набор и все его доли; отдельные таблицы офферов/кампаний не зеркалируют Keitaro

`resource_locks`: уникальный ресурс, случайный владелец и срок блокировки; создание сериализуется по ключу запроса, редактор — по ID кампании

## Состояния и транзакции

Операция: pending → running → completed / failed / unknown; resolved означает, что пользователь явно принял состояние Keitaro после незавершённой публикации

Шаг: pending → running → completed / failed / unknown; running после перезапуска тоже считается неподтверждённой записью

Внутри одной короткой транзакции фиксируется регистрация операции, намерение шага, результат шага либо новая версия черновика; HTTP выполняется после commit намерения и до транзакции результата

Сбой после внешнего успеха до локального commit оставляет running-шаг; повтор сверяется с удалёнными маркерами, вместо создания нового объекта

В процессе публикации поток связан с pending operation; это защищает от новой правки после потери ответа; ключ и параметры публикации остаются доступны через историю

Срок блокировки 10 минут рассчитан на ограниченные внешние запросы и обычный объём тестового трекера; это lease, а не универсальная гарантия для зависшего процесса за пределами срока; для промышленной очереди нужны продление lease/worker и дополнительные гарантии

## Создание

Проверка справочников и оффера → выключенная кампания с детерминированным alias → гео-поток → офферный поток → чтение и проверка → включение

Кампания использует `type=position`, оба потока regular с position 1/2; первый использует фильтр country accept и HTTP redirect, второй — schema landings без фильтра и лендингов, с одним активным оффером

Название не является ключом уникальности: одинаковые названия допустимы для разных намеренных запросов; двойная отправка одного намерения имеет один Idempotency-Key

Незавершённая кампания не удаляется автоматически — сохраняются внешние ID, возможность проверки и продолжения

## Редактор

Fetch получает полный успешный список потоков и каталог офферов до изменения БД; ошибка либо неполная структура ответа не превращается в пустой список привязок

При отсутствии черновика текущие привязки заменяются прочитанными; известные исчезнувшие привязки попадают в archive; новые удалённые сущности, о которых обёртка никогда не знала, восстановить из истории невозможно

При наличии черновика одинаковый удалённый снимок оставляет черновик нетронутым; изменившийся — 409 external_conflict, без частичного применения Fetch

Cancel восстанавливает baseline + archive и удаляет неопубликованные добавления; он не вызывает Keitaro и не является откатом ранее опубликованных изменений

Remove не отправляет DELETE; Push заменяет только массив offers через PUT /streams/{id}; фильтры, редиректы, лендинги и порядок потоков не пересоздаются

Перед Push сравнивается канонический снимок; после него выполняется GET и повторная проверка; идентификаторы связей, timestamps и нормализация null/пустого action_payload не считаются содержательными изменениями

Если публикация неизвестна, можно повторить сверку либо явно принять удалённое состояние; последнее действие отбрасывает черновик, не откатывая удалённые данные

## Доли

Из 100 вычитается сумма закреплённых долей активных привязок; остаток делится целочисленно между незакреплёнными активными привязками; остаточные единицы получают последние элементы в стабильном порядке

Пример: закреплено 25, незакреплённых 2 → остаток 75 → 37 и 38; без закреплений 3 оффера → 33, 33 и 34

Архивные и выключенные привязки имеют отображаемую/публикуемую долю 0 и исключаются из распределения; выключенные связи сохраняют state=disabled

Ограничения: минимум один активный оффер, доли 0..100, сумма закреплений ≤100; если все активные закреплены, их сумма должна равняться 100

## Что не установлено видео

- Какому из равноправных офферов достаётся остаточный процент в общем случае
- Можно ли редактировать долю вручную и как сочетать это с закреплением
- Что делать при удалении последнего активного оффера или недостаточной сумме всех закреплений
- Как Fetch разрешает одновременный локальный черновик и внешнее изменение
- Сохраняется ли закрепление удалённой привязки при Bring back
- Как обрабатываются выключенные привязки

Это документированные решения реализации, а не утверждения о неизвестном поведении исходного редактора: ручная доля автоматически закрепляется; невалидный набор отклоняется; конфликт не затирает черновик; Bring back возвращает незакреплённую активную привязку

## Ограничения интеграции

Публичная OpenAPI неполна относительно action_payload при создании; фактическая передача Google URL и offers проверена на тестовом сервере

API не предоставляет использованный здесь CAS/If-Match, поэтому проверка перед PUT уменьшает риск, но не устраняет гонку с чужой записью между GET и PUT

SQLite предназначен для упрощённого запуска и быстрых тестов; основной вариант — PostgreSQL и межпроцессная сериализация через таблицу блокировок

Локальная БД редактора рассчитана на один настроенный Keitaro; смена трекера требует отдельной БД, чтобы внешние ID разных серверов не пересеклись
